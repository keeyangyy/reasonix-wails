# 压缩与上下文

压缩（compaction）会改写会话历史与请求前缀，涉及卡片定位、跨会话恢复、上下文用量和自动压缩触发。

## 压缩卡片定位

- 卡片是 live 事件产物，不持久化；跨会话/重启靠 sidecar 锚点恢复。
- **不要用轮数做锚点**。后端数 `role=user` 记录、前端渲染 user 气泡，两边对宿主注入处理不一致：`<session-context>`、`<background-jobs>`、轮中插话、工具不可用提示，每新增一种注入就必有一边多算或少算。分页窗口还会让绝对轮数漂移。
- 现在 sidecar 记 `AnchorMessageID`（压缩开始时对话停在哪条消息），前端按消息 id 定位；找不到就不显示，等消息加载进来自然归位。
- `user` 项必须带 `messageID`，否则无从定位。
- 压缩中的卡片没有锚点，落末尾；这是它该在的位置。
- 旧 sidecar 没有 `anchorMessageId` → 重启后卡片不显示，重新压缩一次即可。不要猜位置。

## 跨会话恢复

- 压缩提交必须绑定**压缩开始时**的会话快照，不能用实时 `a.sess.conversation` 比对；切换会话会把已算好的摘要判成 stale 并整份丢弃。
- 投影版本/generation 只在目标会话仍是当前会话时参与否决。
- 前端 pending 卡片用 `usersBefore` 回原位，已完成卡片用 `usersAfter`；`usersAfter=0` 有两义性（刚完成在末尾 / 重启后全在顶部），不要一律按顶部处理。

## 状态刷新

- `compaction_done` 与 `turn_done` 一样刷新会话元数据与上下文；事件序号判重拒绝时仍要执行边界刷新。
- 序号校验只用于丢弃重复的增量行；压缩/回合结束这类状态事件的副作用不能被判重吞掉。
- `history_page`（分页重建，重启/换页真正走的路径）也要保留卡片；任何重建 items 的 action 都要接 `preserveLiveCompactions`。
- 模块级 `liveCompactionsCache` 按 sessionPath 分桶，一个会话只保留最新一张；写测试时每个场景用独立路径，否则卡片会串场。

## 压缩可见性与前缀

- 压缩卡片按锚点恢复原位，不按到达顺序。
- 压缩按钮不能消失；失败要带原因（`compaction.failed` 三语键，`compaction aborted` 事件带原因）。
- 压缩请求要恢复连续前缀，否则 prompt cache 不命中；同时设折叠下限，防止过度收缩。
- fork 落在压缩覆盖区间内时，继承被裁剪的投影。

## 上下文用量

- 右上角读数优先用 provider 上报的 `prompt_tokens` 作为基线，只对“自那次请求以来视图新增长的部分”做估算；无锚点（首次请求、fold 之后、会话重绑）才回退本地估算。
- 锚点记录请求发出时的视图形状与投影版本；provider 回报 usage 时绑定。
- fold 之后锚点必须失效：压缩改变了投影，旧锚点描述的是已经不存在的上下文。
- `usage.Estimated` 为真表示数字是宿主推出来的，不要拿它锚定。
- 增量与锚点用同一套估算相减，比率误差在差值里抵消。

**这个数同时也是自动压缩的触发依据**。口径从“本地估算”改成“provider 实测”后，自动压缩的触发点会变化：以前偏保守，现在更准。改相关逻辑时同时看读数和触发阈值。

## 手动压缩后的上下文刷新

手动压缩不产生新请求，`compaction_done` 只改 items 与 running，不动 `context.used`；自动压缩跑在回合内，后续请求会回填 usage，所以看起来“立即变”。需要刷新时可以：

- A：压缩完成事件直接带压缩后的真实大小（加事件字段）；
- B：压缩成功后前端再要一次快照（多一次往返）。
