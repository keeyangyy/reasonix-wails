# 配置保存

用户配置由 CLI、桌面和 Studio 共用，还与手写编辑共存。保存必须逐键改写，不能整段重写。

## 保存引擎

- **增量优先**：`tomldoc` 把 TOML 解析成可寻址的行文档，`preserve_patch.go` 在其上做逐节、逐元素的差异，提供 setKey / removeKey / insertRegion / removeTables 原子改写。
- **整份重写是兜底**：增量不可表达或回读校验不过时，先把原字节存成 `.rewrite-<时间戳>` 备份，再写整份渲染。刚改的设置必须落盘，丢键必须可见、可恢复。
- 文件不存在或为空时直接写模板。
- 同节内“删键 + 加键”先合并再写，避免重复定义（非法 TOML）。
- 数组表元素（`[[providers]]` / `[[plugins]]` / `[[bot.connections]]`）按 `name` / `id` 对齐，保留本线不认识的元素字段；元素搬移不能把本次有意删除的键写回；无法可靠对齐时走兜底重写。
- 点号键（`a.b = 1`）故意不索引：保留原字节但不寻址，改动落到这类写法就走兜底。

## 跨线保护

- 逐键补丁保留其它线和手写编辑的键；不能整节替换。
- `[serve]` 要纳入渲染，否则保存时会被 `dropUnrendered` 当退役内容删除。
- `[cli]` 退役处理只删 `update_channel`，表内其它键与子表保留。
- 项目配置的显式清理（plugins / sandbox bash / skills / auto guard）继续走整节逻辑，避免两套语义混用。
- 剔除派生 provider 时只认官方内置；自定义 provider 不能因为“文件未声明”就删掉。

## 回读校验

- 两侧都先过一遍加载规范化，避免把加载期派生值（官方模型补齐、注入的 provider）误判成差异。
- 不能要求“补丁后的文本渲染出与目标完全一致”；目标里的派生内容原文件本来就没有，这个判据必然失败。
- 写盘目标侧先剔除派生项，再要求两侧一致。

## 风险入口

桌面所有 setter 最终走 `applyConfigOnly` / `applyConfigChange*` → `loadDesktopUserConfigForEdit` → `cfg.SaveTo`，共用同一保存路径；修复一处覆盖语言、外观、状态栏、Provider、MCP、权限、会话迁移等入口。

例外：`web_search_model_edit.go` 与 `write_access.go` 走自建行级 patch，不进入整份重写分支。

## 验证

- `internal/config` 的 `TestMain` 走 `testenv.RunWithIsolatedUserState`；桌面测试走 `isolateDesktopUserDirs`；夹具落在 `t.TempDir()`，不碰真实用户配置。
- 回归覆盖 Provider / MCP / Agent / 自定义未知字段 / 旧 `config_version` / Studio 兼容字段，以及多次语言切换、保存后重载、并发编辑。
- 随机属性测试守住三条不变量：改到的键生效、自有行按序保留、没触发兜底重写。

## 调试

定位“为什么走了兜底重写”时，在 `patchUserConfigText` 返回 false 与 `looksLikeIntended` 失败两处加临时诊断，把 patched / got / want 三份渲染落盘后 diff，能直接看出哪个元素或键不对称；定位完即删。

`.rewrite-*` 备份是判断“这次保存走了重写”的唯一现场证据。

## 已知限制

无身份键的数组表（`[[bot.routes]]`、`[[bot.desktop_watchers]]`、`[[remote.projects]]`）仍按序号对齐。只改字段、不增删元素时未知字段可保留；一旦增删或重排元素，走整表替换，元素内别的线写的未知字段会丢。这些表目前由本仓库独占，跨线场景暂不存在。`[[bot.connections]]` 已按 `id` 对齐，不受影响。
