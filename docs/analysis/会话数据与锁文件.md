# 会话数据与锁文件

多个 Reasonix 版本（1.38.x Wails、1.39.x、2.x Studio）默认共用 `%APPDATA%\reasonix`。清理数据或排查“某个文件属于哪套”时，先按存储格式判归属，再看锁文件能不能动。

## 一、按存储格式分辨版本

| 版本 | 会话位置 | 特征 |
|---|---|---|
| 1.38.x Wails | `projects\<项目键>\sessions\<时间戳>-<model>.jsonl` | `.events.jsonl` 首行 `schema_version=2`、`type=log`；`.jsonl.meta` 带 `topic_id` / `scope` / `workspace_root` / `head_id` |
| 1.39.x | `desktop-sessions-v5\by-id\<sessionId>\` | 二进制帧 `events.frames`，magic `RX4F`；会话 ID 形如 `desktop-manual-<32位hex>` |
| 2.x Studio | 与 1.38.x 同一个 `projects\...\sessions\` 目录（混居） | `.events.jsonl` 首行 `schema_version=1 或 3`、`type=replace`；`.jsonl.meta` 带 `custom_title` |

1.38.x 与 2.x 写在同一个目录，**不能靠目录名区分**，只能看 `schema_version` 和 meta 字段。

## 二、辅助判据

- **写入时间断层**：已停用版本的登记文件会冻结在某个时间段；在用版本持续更新。
- **exe 二进制字符串**：在对应版本的桌面/宿主 exe 里搜文件名，命中表示该版本引用它；全部未命中且主文件已删，通常可清。
- 统计时注意 `%APPDATA%` 与 `%LOCALAPPDATA%` 是不同根，不要混算。

## 三、锁文件分三类

锁是 `internal/filelock` 的跨进程咨询锁：0 字节 marker，创建后通常不删除。**残留是设计如此，不等于故障。**

| 类别 | 位置 | 处置 |
|---|---|---|
| 活动锁（有主文件） | `repair-mutation-locks\`、顶层 `*.json.lock`、`*.mcp-activation.lock` 等 | 不能删 |
| 活动锁（当前会话） | `projects\*\sessions\subagents\*.lock`、`*.meta.lock` | 不能删 |
| 遗留锁（版本已停用） | 停用版本专用的锁目录，且两版 exe 均不引用 | 可清 |
| 孤儿锁（主文件已删） | 锁名对应的主文件不存在 | 可清 |

清理前至少确认：锁名对应的主文件/队列是否存在、在用版本 exe 是否引用、锁名是否与现存会话匹配。

## 四、清理原则

- **整目录或整类清理**，不要只抽部分文件；内容寻址或哈希链结构抽掉中间项会破坏一致性。
- **活动锁绝不动**：它们被运行中的进程持有；删了会与写入打架。
- 先退出应用，再删；删除走回收站，保留可恢复路径。
- 删后观察一段时间并重启一次，确认应用会重建该重建的、不重建不该重建的；不要只看文件消失。
- 不在应用运行时改活动数据库（如 `topic-state-v1.sqlite`），收益小、风险高。

## 五、适用场景

- 清理旧版本残留、判断某会话属于哪条线、排查锁文件堆积。
- 本仓库与 Studio 共用数据根；跨线操作前先按上表判归属。
