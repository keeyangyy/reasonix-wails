# 缓存与计费

缓存命中率和价格是两套口径，不能混在一起算。

## 缓存命中率

问题：不返回缓存字段的模型（部分网关原样透传，不补 `cached_tokens`）被当成“全部未命中”，把整场命中率拉低。

- `provider.Usage` 增加 `CacheReported`：响应里出现过任一缓存字段（含显式 0）即为真；`mergeSamplingUsage` 跨 attempt 传播。
- 账本与会话统计增加独立的 `ReportedCacheHit/MissTokens`，只累加已上报的调用。
- **计价路径不动**：未上报的调用照旧按全额 prompt 记为未命中，钱不少算。
- 前端命中率用上报对；覆盖率低于 90% 时追加“覆盖 N% token”。

原则：**未上报 ≠ 未命中**。`CacheMissTokens` 同时承担计价与统计两种语义时，缓存率必然失真；用独立累加器分开。

历史数据无法回溯：缓存 token 是累加器，写盘时已经把未上报调用算成全额 prompt，原始信息丢失。金额不同——账本存的是原始报价对象，显示时聚合，所以改读取规则能救历史会话。

## 价格显示

问题：会话级成本采用“全部完整才显示”；任一报价 `Complete=false`，整场价格变成“不可用”。主要来源是根本没有 token 数据的调用（部分网关不回 usage）。

- 入库侧：`EnsureCostQuote` 遇到没有任何 token 计数的调用直接返回 nil，不生成报价、不进账本。
- 读取侧：`Ledger.Total` 聚合时跳过没有 token 计数的桶。**这一半必须做**，否则修复前已落盘的坏桶会让老会话继续显示不可用。
- `Usage.Unknown`（有调用但上游没报用量）**不跳过**：可能真的花了钱，仍生成 `usage_unknown` 报价。
- 有 token 但缺价的调用仍计入并标记不完整；那确实少算了钱，应让用户看见。
- 全空账本仍显示“不可用”，不要显示 ¥0.00。

### 恢复与来源明细

- 恢复账本时运行时报价被置空，面板会退回磁盘上的旧结论；恢复时要用 `Ledger.Total` 重算一次。
- 来源明细不能再用独立累加器（只在整场聚合成功时加钱，失败后金额冻结）；改为从账本按来源分组聚合，与总额同源。
- 面板取数时若运行时报价为空但账本存在，就地聚合一次，避免“必须发消息才显示”。

### 前端判据

零价是有效价格，不是缺失；相关判据用 `>= 0`，不要用 `> 0`。

## 回归点

- 新增 usage 字段时，确认解析层、聚合层、账本、wire、单轮面板都带上 `CacheReported`；漏一层就会出现“整列未返回”或单轮 0%。
- `prompt_tokens_details` 非 nil 即视为已上报；显式 `cached_tokens: 0` 是“上报了 0”，不是“没上报”。
- 不要把“跳过不完整报价”当成通用修法：有 token 但没价格的调用会因此少算钱。
