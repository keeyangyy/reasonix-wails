## 一、派发节奏（用户最关心的问题）

排入三条 followup 后放行首回合，实测派发序列：

```
[turn-0, q1, q2, q3]
第 1 条派发 = "q1"（独立回合）
第 2 条派发 = "q2"（独立回合）
第 3 条派发 = "q3"（独立回合）
结束时 inbox items=0 paused=false
```

- 每条都有独立 `TurnDone`，各自成回合，**不会合并成一整轮**。
- 单条 followup 只派发一次，不重复。
- 派发完成后队列清空，不残留 `paused`。
- 对照确认：`EnqueueInbox` 自身不触发派发（被动排队），`TryEnqueueFollowup` 在空闲时会 kick 一次。

## 二、队列操作

| 操作 | 行为 |
| --- | --- |
| 新增 | 按到达顺序追加；混合 intent 也保持到达序 |
| 修改 | 改文本、**位置不变**、revision 递增（1→2） |
| 删除 | 删中间项其余保持；全删后队列空且 `paused=false` |
| 移动 | 上移/下移正确；越界钳到末尾、负索引钳到 0 |
| 跨 intent 移动 | **只改物理位置，不改 intent** |

## 三、两个列表的切换

三个操作语义不同，容易混淆：

| 操作 | 改 intent | 改 state | 移动位置 |
| --- | --- | --- | --- |
| `ConvertIntent` | 是 | 否（仍 `queued`） | 否，原地 |
| `AcceptSteer` | 否 | 是 → `steer_accepted` | 是，移到队尾 |
| `ReleaseAcceptedSteer` | 是 → `followup` | 是 → `queued` | 已在队尾 |

**`ReleaseAcceptedSteer` 回退 intent 是关键**：前端按 intent 分组，若只回退 state，退回的行仍会被钉在本轮列表。

非法切换均正确拒绝（`ErrInvalidState`）：对 `steer_accepted` 调 `ConvertIntent`、对 `queued`/`steer_consumed` 调 `Release`、移动 `steer_accepted` 项。

## 四、缺陷一：折叠时本轮插话被截掉

**位置**：`desktop/frontend/src/components/ComposerGuidanceShelf.tsx:73`

```ts
const visible = expanded ? items : items.slice(0, 2);  // 先截断
...
const ordered = [...visible].sort(...)                  // 后排序
```

先取前 2 条再排序。而 `AcceptSteer` 会把本轮项移到存储队列**末尾**，于是：

| 存储顺序 | 折叠显示 | 结果 |
| --- | --- | --- |
| `[候选A, 本轮A]` | `[本轮A, 候选A]` | 正常 |
| `[候选A, 候选B, 本轮A]` | `[候选A, 候选B]` | **本轮A 消失** |
| `[候选A, 候选B, 候选C, 本轮A]` | `[候选A, 候选B]` | **本轮A 消失** |

`guidanceExpanded` 默认 `false`（折叠），所以只要有 2 条以上候选，再插入本轮插话，界面上就看不见它。展开状态全部正常。

**修法**：把截断放到排序之后（先排好两组再取前 2 条），并保证本轮组优先保留。

## 五、缺陷二：进程重启后队列冻结

`internal/sessioninbox/store.go:214` 起：进程启动时若 `manifest.RunID` 与当前进程不同且队列非空，无条件 `Paused = true` 并标 `Recovered`。`ProcessRunID()` 每进程一个随机 UUID，因此**只要上次退出时队列非空，下次启动必中**。

实测：重启前 `paused=false`，重启后 `paused=true`、`NextQueued()` 恒 `false`，连开三次都不自愈。Controller 层同样复现：2 秒内无派发，手动点「继续执行」后立即派发。

这与界面上「收件箱已暂停」横幅（含「查看队列 / 继续执行 / 保持暂停」）是同一状态的两个表现。

## 六、待确认项

- **派发内容带 runtime policy 前缀**：测试日志显示实际派发文本为 `<reasoning-language>…</reasoning-language>` + 用户原文。是否为设计意图待确认。
